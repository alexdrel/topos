# Topos Specification v1.0

**Topology is Semantics. Layout is Logic. Code is Visual.**

# The Topos Manifesto
### The Problem
We are trapped in a trilemma when creating architectural diagrams:
1.  **The Code Trap (Mermaid):** We gain speed and diffs but lose **Spatial Meaning**. We cannot define "Group A sits below Group B," destroying the architectural context.
2.  **The Canvas Trap (Visio):** We gain layout control but are trapped in unmaintainable binary blobs that cannot be version-controlled or generated by AI.
3.  **The ASCII Trap:** We gain portability but lose **Aesthetics**. ASCII diagrams look like 1980s comments, not professional documentation.

### The Solution: Topos
**Topos** is a toolchain that creates a "Living Chart." It decouples **Intent** (The Napkin), **Topology** (The Map), **Logic** (The Legend), and **Aesthetics** (The Skin).

---

### The Anatomy of a Topos File
A Topos chart is composed of four sections, separating structure from presentation.

#### 1. The Napkin (The Intent)
*   **Role:** The Prompt / Scratchpad.
*   **Format:** Natural Language or Visual DSL.
*   **Philosophy:** **"LLM-Native."** The user (or Copilot) types intent: `[User] -> [API]`. The Engine interprets this sketch to generate the strict Map.
*   *Lifecycle:* Ephemeral. Used to generate the Map, then cleared.

#### 2. The Map (The State)
*   **Role:** The Source of Truth for **Topology**.
*   **Format:** ASCII / Unicode Grid.
*   **Philosophy:** **"What You See Is What You Git."** The Map defines existence, position, grouping, and primary "hard" connections. It is human-readable in a code editor and clean in a Git diff.

#### 3. The Legend (The Logic)
*   **Role:** The Source of Truth for **Semantics**.
*   **Format:** Declarative Key-Value.
*   **Philosophy:** **"Layering, Not Duplication."**
    *   **Enrichment:** Adds labels/properties to Map lines.
    *   **Overlays:** Defines "soft" connections (curves) that would clutter the Map.
    *   **Metadata:** Defines Realms and Zones.

#### 4. The Skin (The Style)
*   **Role:** The Source of Truth for **Aesthetics**.
*   **Format:** CSS / Theme Definition.
*   **Philosophy:** **"Theming over Hardcoding."**
    *   The Map defines a box. The Skin defines if it is blue, shadowed, or flat.
    *   The Map defines a cylinder `()`. The Skin defines if it renders as a flat icon or a 3D isometric database.
    *   Allows for "Dark Mode" diagrams or Corporate Branding without touching the architecture source.

---

### The Workflow: "Script, Stitch, Sculpt, Paint"

#### Phase 1: Script (Napkin)
The user dumps their brain onto the Napkin.
*   *Input:* `[Client] -> [LB] ... [LB] v [API]`
*   *Goal:* Speed. No formatting.

#### Phase 2: Stitch (Compile)
The Engine consumes the Napkin and generates the **Map** and **Legend**.
*   It calculates grid layout.
*   It draws the boxes/pipes in Unicode.
*   It pushes complex labels to the Legend.

#### Phase 3: Sculpt (Maintain)
The user edits the Map directly.
*   *Action:* Manually nudging a box to align it perfectly.
*   *Benefit:* Because the Map is text, the user has total control over layout.

#### Phase 4: Render (SVG Generation)
The final artifact is generated by combining all layers.
*   **Shape Inference:** The renderer sees Unicode Arcs `╭──╮` and renders rounded SVG vectors. It sees `( )` and renders Database icons.
*   **Smart Merging:** It combines the **Map's coordinates** with the **Legend's metadata** and the **Skin's colors**.
*   **Result:** A professional, vector-based SVG that looks like it was made in a high-end design tool, but originated from text.

### The Vision
Topos turns the diagram into **Infrastructure as Code**.
It allows the Architect to sketch, the AI to draw, the Engineer to maintain, and the Designer to style. It is the end of "Rotting Diagrams."

## 1. File Structure

A Topos file (`.topos`) defines a diagram through four optional sections, each introduced by a colon-prefixed header.

```topos
:napkin
[Intent / Sketch]

:map
[Spatial Grid / Topology]

:legend
[Semantics / Logic / Properties]

:style
[Aesthetics / CSS]
```

---

## 2. Section: `:napkin` (The Intent)

**Role:** Ephemeral scratchpad.
**Format:** Unstructured or semi-structured text.
**Purpose:** "LLM-native" input. The user describes *what* they want; the engine generates the `:map`.

```topos
:napkin
User -> Load Balancer -> Web App
Web App -> [Database, Cache]
```

---

## 3. Section: `:map` (The Topology)

**Role:** The Source of Truth for **Layout** and **Existence**.
**Format:** ASCII / Unicode Grid.
**Principles:** "What You See Is What You Git."

### 3.1 Entities
Entities are defined by their visual boundaries on the grid.

| Type | ASCII | Unicode | Meaning |
| :--- | :--- | :--- | :--- |
| **Box** | `[ Label ]` | `┌ Label ┐` | Standard Node / Component |
| **Actor** | `< Label >` | `< Label >` | Actor / Space-saving Node |
| **Rounded** | `( Label )` | `( Label )` | Generic Rounded Node (e.g. Storage, Process) |
| **Region** | `┌── Label ──┐` | `┌── Label ──┐` | Container / Zone |

**Note:** ASCII and Unicode are interchangeable. The renderer infers shapes based on the wrappers.

### 3.2 Inline Sigils
Properties can be defined directly inside the Map entity for convenience.
- `#id`: Unique Identifier
- `.class`: Style Class

```topos
┌──────────────────┐
│   API Gateway    │
│ #gateway .public │
└──────────────────┘
```

---

## 4. Section: `:legend` (The Semantics)

**Role:** The Source of Truth for **Logic**, **Flows**, and **Properties**.
**Format:** Key-Value / DSL.
**Purpose:** "Layering, Not Duplication." Everything that clutters the Map goes here.

### 4.1 Syntax
```topos
Selector : Property .class key=value
```

### 4.2 Selectors
- **By ID:** `#gateway`
- **By Label:** `[API Gateway]`
- **By Type:** `<User>`
- **Multiple:** `[A], [B]`

### 4.3 Connectors
Connectors are treated as explicit relationships.
- `->` : Standard directional
- `<->`: Bidirectional
- `~>` : Curved / Virtual (Route independently of grid)
- `..>`: Dotted / Weak / Virtual

### 4.4 Properties & Assignments
```topos
#gateway : "Main Entry" .critical version=2.0
```

### 4.5 Hierarchies & Deep Nesting
For details too complex for the text grid:
```topos
[Main App]:
  - [Auth Service]
  - [Payment Service]
```

### 4.6 Flows (Multi-hop)
Defining full pathways for highlighting/animation:
```topos
<User> -> #gateway -> [Auth Service] -> (DB) : flow="Login Process" .animated
```

---

## 5. Section: `:style` (The Aesthetics)

**Role:** The Source of Truth for **Visuals**.
**Format:** CSS-like syntax.
**Purpose:** "Theming over Hardcoding."

```css
:style
.critical {
  stroke: #ff0000;
  stroke-width: 3px;
}

(DB) {
  shape: cylinder;
  fill: #eee;
}

#gateway {
  icon: url(/icons/gateway.svg);
}
```

---

## 6. Rendering Pipeline

1.  **Parse `:napkin`** (Optional): Generate `:map` proposal.
2.  **Parse `:map`**: Build spatial graph. Resolve inline IDs/Classes.
3.  **Parse `:legend`**: Apply properties, build flows, overlay virtual connections.
4.  **Parse `:style`**: Apply visual themes.
5.  **Render**: Output SVG/Canvas.
